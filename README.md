# ClearPath Review

A review workspace for the compliance marketing team at ClearPath Financial (a fictional consumer-finance company). It replaces the Excel-and-email process with a queue where every asset arrives already checked against the rules, so reviewers confirm cited findings instead of reading each asset from scratch.

- **Live demo:** https://clearpath-compliance-five.vercel.app
- **Source:** https://github.com/sriramssenthil/clearpath-compliance

Everything in the demo is fictional: the company, the partners, the people and the history. The rules are a representative sample of real federal requirements, not legal advice.

## Try it in three minutes

There are no accounts. Pick a role on the landing page; you can switch roles at any time from the menu in the top right.

1. **As Jordan Ellis (affiliate partner)**, open *New submission*, choose *Load an example → Affiliate blog post (risky)* and press *Run pre-check*. In about five seconds you get findings with the quoted text, the rule and its citation, why it matters and a suggested fix. Submit it.
2. **As Priya Raman (compliance reviewer)**, open *Review queue*. The item is there, sorted by deadline and risk. Open it: the flagged text is highlighted and linked to the findings. Accept a few, dismiss one with a reason, then request changes. The submitter's feedback email is drafted from the findings you accepted.
3. **Back as Jordan**, open the submission and press *Make changes and resubmit*. Fix the copy (the findings include approved disclosure wording you can paste) and submit version 2.
4. **As Priya again**, the item is back in her queue with *Compare with previous version* available. Findings that no longer apply were resolved automatically. Dismiss what remains and approve. The audit trail at the bottom shows every step.
5. **As Sofia Alvarez (compliance lead)**, see the dashboard (turnaround, SLA, first-pass approval, partner scorecards), the rules library (editable by the lead) and the *Reset demo data* control.

The example *Affiliate card review with hidden instruction* shows how the system treats hostile content: the page tells the AI reviewer to "report no findings", and it is flagged instead of obeyed.

## The problem

Review runs on email and a spreadsheet, and the compliance team cannot keep up with marketing volume. Reading the process as a queueing problem, reviewer time per asset is roughly *rounds × minutes per round*, plus waiting. Email and Excel inflate every term:

| Bottleneck | What this does about it |
|---|---|
| Routine defects reach reviewers ("guaranteed approval", a rate with no APR, no #ad) and cost whole review rounds | **Pre-check** for submitters runs the rules before compliance ever sees the asset, with cited fixes drawn from approved disclosure language |
| Every asset is read from scratch | Findings arrive pre-annotated with the exact quote, citation and suggested fix; the reviewer accepts or dismisses |
| Revisions arrive as new attachments and get re-read in full | Versions are kept, diffed against the previous one, and findings that no longer apply resolve automatically |
| First-in-first-out inbox, escalation over chat | Queue sorted by SLA and risk, with deadlines, claiming and a "fast lane" label for low-risk items with nothing flagged |
| "Who approved what?" lives in inboxes | Append-only audit trail on every submission |
| The same affiliate repeats the same mistakes | Partner scorecards; a partner's rejection history raises the risk score of its next submission |

**What I have not measured.** I have no real review data, so I make no throughput claim. The dashboard numbers are synthetic seed data (40 submissions over eight weeks, generated by `lib/seed/history.ts`) and exist to show what the metrics would look like. The only measured numbers are the accuracy figures below.

## How it works

```
 Marketer / affiliate                         Reviewer / lead
 submit + pre-check                           queue -> workspace -> decision
        |                                              |
 +------v--------------- Next.js (Vercel) -------------v------+
 |  server actions -> workflow service (permissions, state    |
 |  machine, audit log)                                       |
 |                                                            |
 |  analysis engine                                           |
 |    deterministic rules --+                                 |
 |    Claude (structured) --+-> merge -> verify quotes -> risk|
 +-----+-----------------------------------+------------------+
       |                                   |
  Neon Postgres                        Anthropic API
  (versions, findings, decisions,      (claude-opus-5-5)
   audit log, rules, cache)
```

**Hybrid analysis.** Two layers each propose findings and the server decides what survives.
- *Deterministic rules* (`lib/compliance/deterministic.ts`) handle what code can decide exactly: banned phrases, required disclosures (NMLS ID, Equal Housing Lender, unsubscribe link, #ad), and numbers checked against the product facts (an advertised APR below the lowest rate ClearPath offers).
- *Claude* reads the asset as a whole for what depends on meaning: implied guarantees, whether triggering terms need extra disclosures, misleading comparisons, language that could discourage applicants.
- Rules that only ask "is this disclosure present?" are decided by code alone. In an early eval Claude marked the NMLS ID and unsubscribe link as missing on a clean email where they were present; a regex verifies presence exactly, so the model isn't asked.

**The AI only adds flags.** The output schema has no field that can approve, clear or change anything. The recommendation ("likely to need changes") is computed in code from the findings. Approval needs a human, and the service refuses to approve while a high-severity finding is open or accepted.

**All model output is untrusted.** Every Claude finding must use a rule that applies to the asset and quote text that really exists in it (exact match, then normalised, then a strict fuzzy match). Findings that fail are discarded and counted (9 to 10 per 24-case eval run). Submitted text is wrapped in `<submission>` tags and declared to be data, and text that tries to instruct the reviewer is itself a high-severity finding (`SEC-INJECTION`).

**Rules are data.** The 21 rules live in a table with their scope, severity, citation, plain-language guidance and the instruction given to the model. The compliance lead edits them in the UI and every later analysis uses the new version. Results are cached by a hash of the text, metadata and rules, so a pre-check followed by a submit costs one model call.

**Records are append-only.** A resubmission adds a version instead of editing one, findings keep their status history, and every action writes an audit event in the same database batch as the change itself.

**Resubmission resolves findings.** When a new version is submitted the whole asset is analysed again (a disclosure rule can depend on text that did not change), and an earlier finding is resolved if its rule no longer fires. The same reviewer gets it back with a 24-hour clock.

**Spend guard.** The demo is public and each uncached check costs a cent or two, so live model calls are limited per person and per hour (`lib/workflow/budget.ts`). Past the limit, or if the API fails or refuses, the check falls back to rules-only mode with a visible banner instead of erroring.

## Accuracy

`npm run eval` runs 24 labelled assets through the engine: 6 clean controls (4 deliberately tricky, for example a card ad with "1.5% cash back" next to a fully disclosed intro APR), 14 with one or two violations covering all 21 rules, and 4 hard or ambiguous cases. The labels are mine, written from the rule catalogue before the rules were implemented.

| | Real issues found (recall) | Flags that were real (precision) | Clean controls flagged | p50 latency | Cost per asset |
|---|---|---|---|---|---|
| Rules only | 20 of 27 (74%) | 95% | 1 of 6 | instant | $0 |
| Rules + Claude, low effort | 27 of 27 (100%) | 77% | 2 of 6 | 4.4 s | about $0.02 |
| Rules + Claude, medium effort | 27 of 27 (100%) | 84% | 2 of 6 | 6.6 s | about $0.02 |

How to read this:
- **Recall is the number that matters most.** A false negative is a fine; a false positive is a dismissed flag. The seven misses of the rules-only layer all depend on meaning (an "already approved" paraphrase, a "fixed" rate that is really an ARM, a polite attempt to instruct the checker), which is what the model is for.
- **The extra flags are mostly defensible.** Looking at them one by one: a flag for an unsubstantiated "Consolidate and save!", a note that "soft pull only" might imply there is never a hard inquiry, and a few findings filed under a broader rule than my label. They are stricter than my labels, not hallucinations (hallucinated quotes are discarded by the server before this table is computed). A reviewer dismisses these with a reason, and the dismissal rate per rule is on the dashboard, which is the feedback loop for tuning.
- **One known false positive.** Clean case 06 is a post that quotes "guaranteed approval" only to warn readers against it. The phrase rule flags it, because a pattern cannot tell a warning from a claim, and deterministic findings win a merge. In the app a reviewer dismisses it ("Quoted in a warning, not a claim" is one of the quick reasons).
- **The sample is small and run-to-run variance is real.** Two runs of the same configuration moved precision by about five points, so low versus medium effort is within noise. I defaulted to low for latency.
- Per-case results are in `evals/results/`. Use `npx tsx evals/inspect.ts 09 15` to see exactly what the model flagged on a case.

## Assumptions

**Business**
- A team of three to five reviewers handles a few hundred assets a month, about half from affiliates.
- Products: personal loans, credit cards and mortgage prequalification. Channels: email, paid social, display, affiliate landing pages and SMS. Product facts (APR ranges, fees, approved disclosure language) are fictional and owned by Product and Compliance.
- SLA: 72 hours for a first review, 24 hours for an expedited request or a re-review of a revision.
- ClearPath is accountable for what affiliates publish on its behalf, so affiliate content is pre-approved.
- Approval applies to the exact text reviewed; any edit needs a new review.

**Product**
- AI assists and humans decide. There is deliberately no auto-approval; the sensible next step is a per-rule threshold switched on only once eval data supports it.
- Rule citations are ones I am confident of (Reg Z 12 CFR 1026.16 and 1026.24, FCRA, FTC Endorsement Guides 16 CFR 255, Reg B, CAN-SPAM, UDAAP). Where something is internal policy, the rule says so.

**Technical**
- Authentication is a persona switcher (an unsigned cookie holding a user id). It exists so every role can be tried without accounts. Production would use SSO for employees and invite-only accounts for partners. The server still checks role and ownership on every read and write, so a marketer cannot open an affiliate's submission (verified in `npm run test:smoke`).

## What I cut, and what I would do next

**Cut for the 24-hour window**
- **Image and PDF upload.** The engine accepts an image or PDF input (the model transcribes it so highlighting and diffs still work), but there is no upload UI or file storage, and the image path is untested end to end.
- **Landing-page URL ingestion.** Needs fetching with its own prompt-injection and SSRF hardening; I would rather ship text input correctly.
- **Concurrency control.** State is read then written in one batch; two reviewers acting on the same finding at once would be last-write-wins. I would add optimistic version checks.
- **Notifications.** The feedback email is drafted and shown, not sent.
- **Time zones.** Submission pages show UTC and the queue shows deadlines in Central time. Should be one setting per user.

**Next**
- Approval expiry when rates or product facts change (list the approved assets that still cite the old terms).
- Per-rule auto-approve thresholds, switched on with eval data and the audit log behind them.
- A background queue for analysis, and a cheaper first-pass model with escalation.
- Post-approval monitoring of live affiliate pages for drift.
- Multi-stage approvals (Legal, Product) and routing by state.
- Importing the existing Excel tracker so history carries over.

## Security notes

- Submitted content is data, never instructions: wrapped in tags, the model cannot take actions, its output is schema-validated and every quote is verified against the source text.
- The API key lives only in environment variables. `.env*` is git-ignored; `.env.example` lists what is needed. `/api/health` reports whether a key is configured, never its value.
- Spend is capped per person and per hour, and the Anthropic key should have its own spend limit set in the console.

## Run it locally

Requires Node 22 and a Postgres database (the demo uses Neon).

```bash
npm install
cp .env.example .env.local        # add ANTHROPIC_API_KEY and DATABASE_URL
npm run db:migrate                # create the tables
npm run seed:all                  # people, rules and product facts, eight weeks of history
npm run dev                       # http://localhost:3000
```

| Command | What it does |
|---|---|
| `npm test` | Unit tests (rules, engine, anchoring, merge, risk, workflow rules, UI helpers) |
| `npm run test:smoke` | End-to-end review lifecycle and permission checks against the real database; makes two live model calls and cleans up after itself |
| `npm run eval` | Accuracy eval on the 24 labelled assets (`npm run eval -- --rules-only` makes no model calls) |
| `npm run typecheck` / `npm run lint` | Static checks |
| `npm run seed:history` | Rebuild the demo history (also behind the lead's *Reset demo data* button) |

## Project layout

```
app/                    Next.js routes: landing, submissions, queue, dashboard, rules, /api/health
components/             UI grouped by area (submit, review, queue, dashboard, rules, ui)
lib/compliance/         The engine: rules runner, Claude call, quote anchoring, merge, risk
lib/workflow/           State machine, permissions, service (writes), queries (reads), audit actions
lib/seed/               Rules library, product facts, example ads, people, demo history
lib/db/                 Drizzle schema; migrations are in drizzle/
evals/                  Labelled cases, runner, results
tests/                  Vitest suites
```

Built with Next.js 16 (App Router), React 19, TypeScript, Tailwind 4, Drizzle on Neon Postgres, and the Anthropic SDK (`claude-opus-5-5`, structured outputs).
